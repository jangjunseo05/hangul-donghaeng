# 로컬 E2E 기록 — 2026-11-06 (대체 모델 · 파이프라인 검증)

> **파이프라인 검증 · 모델 품질은 배포 모델(L40S Nano-12B-v2-VL)과 별개.**
> 이 시험은 배포 모델로 돌린 것이 아닙니다. 아래 성공률과 판단은 대체 모델의 결과이며 배포 모델의 정확도나 안정성을 보여 주지 않습니다. OpenShell도 사용하지 않았습니다.

### 대체 모델을 고른 근거

hosted `nvidia/nemotron-nano-12b-v2-vl`은 HTTP 410 `"reached its end of life on 2026-08-26"`을 반환합니다. 같은 키로 조회되는 Nemotron VL 계열 후보는 두 개였고, 둘 다 reasoning 모델입니다. thinking을 켜 둔 기본 상태에서는 content가 비고 `finish_reason=length`로 끝납니다. 두 모델 모두 `chat_template_kwargs.enable_thinking=false`로 해결됐습니다. `/no_think` 시스템 문구만으로는 해결되지 않았습니다.

| 후보 | 응답 model 일치 | 실제 Decision 프롬프트(사진 1장) |
|---|---|---|
| `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning` | 일치 | **2/2 실패**: 답 대신 JSON 스키마 껍데기(`{"additionalProperties":…, "properties":{…}}`)를 반환함 |
| `nvidia/nemotron-3.5-super-vl-120b-a12b` | **불일치**(별칭) | 1회에 스키마 통과. 현판을 읽어 광화문으로 판단 |

일치성은 30B가 낫지만, 30B는 제품 프롬프트의 출력 형식을 따르지 못해 파이프라인 검증이 불가능했습니다. 그래서 120B를 골랐습니다. 응답 model 불일치는 숨기지 않고 로그에 `false`로 남깁니다. 반환된 이름 문자열은 신뢰할 수 없는 값이라 로그에 남기지 않습니다.

## 발견한 버그와 수정(코드 `f659db4`·`a5787cf`·`34d249f`·`48b2713`·`82ef73a`, 문서 정정은 후속 docs 커밋)

1. **F2 관련성 판정이 UI 기본 질문에서 틀림.** 영어 기본 질문은 한국어 자료와 단어가 겹치지 않았고, "is"가 파일명 `list`에 걸려 음식 목록을 관련 자료로 판정했습니다. 그 결과 02·03은 `irrelevant`, 04는 `used`가 됐습니다. 한국어 기본 질문도 "열고"가 음식 목록의 "문을 열고"에 걸렸습니다. 수정: 질문의 내용어만 쓰도록 바꿨습니다. 한국어는 2자 이상 단어 중 일반 의문어·동사(`KO_STOP`)를 빼고, 2자 단어는 단어 시작에서만, 4자 이상이면 3자 어간으로도 맞춥니다. 영어는 3자 이상 단어 중 불용어를 빼고 복수형을 줄여 단어 시작에서 맞춥니다. 가상 자료에는 영어 이름 "Haeon Palace"를 넣었습니다. 테스트를 추가했습니다(기본 질문 3종의 worker와 broker 재검증, 불용어/부분 문자열, "해온궁 근처 밀면", "몇 시에 닫아요", "fee"/"tickets").
   - 실시간 3~5회차는 `f659db4`의 앞선 규칙(한국어 3자 이상, 영어 4자 이상)으로 실행했습니다. `a5787cf`·`34d249f`는 코드 리뷰 지적(짧은 내용어 누락, 한국어 기능어 포함, 2자 단어의 부분 일치)을 반영해 규칙을 다듬은 것입니다. UI 기본 질문 두 개와 시험 질문에서는 두 규칙의 관련성 판정이 같습니다(01·02·03·05 관련, 04 무관). 그래서 위 F2 결과는 바뀐 규칙에서도 유효하지만, 바뀐 규칙으로 실시간 재실행은 하지 않았습니다.
2. **F2 프롬프트에 항목 형태가 없음.** 실제 모델이 quote를 객체가 아닌 문자열로 보냈습니다. 수정: `REVIEW_SYSTEM`에 claims/conflicts/source_judgments 형태를 명시하고, 스키마와 일치하는지 검사하는 테스트를 추가했습니다.
3. **F2 검증 코드가 repair에 전달되지 않음.** `ungrounded_judgment`와 `judged_source_supports_claim`이 `CHECK_CODES`에 없어서, 모델은 "invalid_model_output"만 받고 같은 답을 반복했습니다. 수정: 코드와 수정 힌트를 추가하고 테스트했습니다.
4. **hosted 기본 모델 EOL.** 코드 기본값과 `.env.example`이 410을 반환하는 모델을 가리킵니다. 코드 기본값은 배포 동작을 바꾸지 않도록 그대로 두고, 이 기록과 같은 후속 docs 커밋에서 README, agent/README, .env.example에 EOL과 "hosted는 대체 경로가 아님"을 명시했습니다.
5. **상태 표시의 근거 부족.** `model_configured`는 broker env에 키가 있는지만 봅니다. 그래서 키가 worker에만 있는 정상 구성에서도 ✗로 표시됩니다. 실제로 쓰는 모델 이름도 화면에 하드코딩돼 있었습니다. 추가: `health.worker_model`(worker 자기 보고 라벨, 증명 아님)과 `NVIDIA_DISABLE_THINKING`(기본 off). 응답 model 불일치는 이제 `false`로 기록합니다. `worker_model`은 worker가 연결돼 있을 때만 표시되며, 쓸 수 없는 모델 ID는 보내지 않아 `null`이 됩니다. web 표기(배지, 리본, 상태 창)는 web 담당 커밋에서 별도로 수정합니다.

6. **(실데이터 화면에서 발견) F2 판정과 사유가 맞지 않음.** 모델이 쓸 수 있는 판정이 outdated와 conflict_superseded뿐이라, 주제가 다른 03을 outdated로 넣었습니다(메모는 "역사 정보만 있음"). 수정: 같은 사실에 다른 값이 있을 때만 판정하고, 주제가 다른 자료는 판정하지도 인용하지도 않게 했습니다(`48b2713`). 결과는 위 6회차와 같습니다.
7. **(실데이터 화면에서 발견) 근거 카드가 전부 "날짜 없음"으로 표시됨.** 출처 자체에 날짜가 없어서 `as_of=null`이고, 이는 정직한 값이므로 바꾸지 않았습니다. 대신 팀이 출처를 확인한 날짜를 broker 전용 `GET /api/evidence/observed`로 제공합니다. 화면에는 "확인일"로만 표시해야 하며, 화면 반영은 web 담당 커밋에서 합니다.

## 미확인 · 한계

- 배포 모델(Nano-12B-v2-VL)로 F2를 실행한 적은 아직 없습니다. 위 F2 결과는 대체 모델 결과입니다. 수정 1~3은 모델과 무관한 버그라 배포 모델에도 적용되지만, 배포 모델의 판정 안정성은 L40S 재배포 후에 따로 확인해야 합니다.

- 대체 모델의 출력 형식 위반(가끔 `invalid_model_output`)은 배포 모델의 동작을 예측하지 않습니다.
